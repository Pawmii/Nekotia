# Архитектура Nekotia

## Конвейер сборки

```
nekotia.json ──► nekoc build
                  │ ProjectConfig: собрать *.cs / *.neko из sdk/ и kernel/ (без bin/ obj/)
                  │ Desugarer:     .neko → C# (CodeMask пропускает строки и комментарии, строки не сдвигаются)
                  │ Roslyn:        CSharpCompilation против System.Private.CoreLib (только для атрибутов и примитивов)
                  │                ошибки CS* → стоп
                  │ CppEmitter:    символы + семантическая модель → C++
                  ▼
        build/gen/nekotia.gen.hpp   forward-декларации → enum → struct (топосорт по полям) → static class
        build/gen/nekotia.gen.cpp   статические поля → тела методов (#line перед каждым оператором) → neko_kernel_main
                  │
clang++ (freestanding, -mcmodel=kernel, -mno-red-zone, без SSE) ──► *.o
                  │  + runtime/src/core, freestanding, arch/x86_64 (boot.cpp, idt.cpp, isr.S, serial.cpp)
ld.lld -T runtime/src/arch/x86_64/linker.ld ──► build/nekotia.elf
xorriso + limine bios-install ──► build/nekotia.iso (гибрид BIOS/UEFI)

user/NAME/nekotia.json ("target": "user") ──► nekoc build ──► build/user/NAME/gen/*.cpp
clang++ (freestanding, ring 3) + runtime/user (crt0, user.cpp) + core/math.cpp + freestanding/libc.cpp
ld.lld -T runtime/user/linker.ld (0x400000) ──► build/user/bin/NAME
tar (ustar) build/user/bin/* + initrd/* ──► build/initrd.tar ──► /boot/initrd.tar на ISO
                                                  (module_path в boot/limine.conf → модуль Limine → VFS /)
```

## nekoc (`tools/nekoc`)

| Файл | Роль |
|---|---|
| `Program.cs` | CLI: `build`, `check`, `desugar`, `version`; `--format json` для редактора |
| `ProjectConfig.cs` | чтение `nekotia.json` |
| `Sugar/Desugarer.cs`, `Sugar/CodeMask.cs` | переписывание сахара в C# |
| `Compiler/Driver.cs` | разбор, компиляция Roslyn, запуск эмиттера, запись файлов (только при изменении) |
| `Compiler/CppEmitter*.cs` | генерация: объявления, операторы, выражения |
| `Compiler/TypeMapper.cs` | C#-тип → C++-тип |
| `Compiler/Symbols.cs` | атрибуты SDK, экранирование имён (ключевые слова C++ → `name_`) |
| `Compiler/Diagnostics.cs` | диагностики в формате MSBuild (`$msCompile`) и JSON |

Ключевые решения:

- **Один translation unit** для всего C#-кода: инлайнинг между модулями, шаблоны без явных инстанциаций,
  простой порядок объявлений. При росте ядра — разбиение по файлам (фаза 1).
- **Семантика C# важнее красоты C++**: неявные числовые преобразования, которые в C++ дали бы другой результат, становятся
  явными кастами; аргументы перегруженных методов приводятся к типам выбранной Roslyn'ом перегрузки.
- **`#line`**: каждое C#-выражение-оператор помечается исходной строкой — clang-ошибки, `addr2line` и gdb работают в терминах C#.
- **Сахар — препроцессор, а не новый парсер**: Roslyn остаётся единственным источником истины о C#; `defer` кодируется
  валидным C# (`if (Sugar.Defer) stmt;`) и распознаётся эмиттером по символу.

## Рантайм (`runtime/`)

```
include/neko/types.hpp    fnptr, defer guard, NEKO_ENUM_OPERATORS, NEKO_ASM*
include/neko/boot.hpp     BootInfo, Framebuffer (поля = поля C#-структур SDK)
include/neko/cpu.hpp      hlt/cli/sti, in/out, cr2/cr3, rdtsc (в host-режиме — заглушки)
include/neko/memory.hpp   mem::*, heap::*, pmm::*
include/neko/serial.hpp   serial::*, str::*
src/core/                 heap.cpp, pmm.cpp, print.cpp (+ panic)
src/freestanding/         memcpy/memset/memmove/memcmp, new/delete, __cxa_* заглушки
src/arch/x86_64/          boot.cpp (kmain), idt.cpp + isr.S, serial.cpp, linker.ld
src/host/                 host_main.cpp — платформа «Linux-процесс»
```

### Загрузка (x86_64)

1. Limine (BIOS или UEFI) загружает ELF по адресу `0xffffffff80000000`, включает long mode и paging, отображает
   физическую память в HHDM, даёт 64 KiB стека и передаёт управление `kmain`.
2. `kmain`: COM1 → base revision → своя GDT/TSS (IST для #DF/NMI/#MC) → IDT (256 векторов) → память (куча, фреймы) →
   framebuffer-консоль → ACPI (RSDP → XSDT → MADT) → APIC: 8259 замаскирован, LAPIC включён, таймер 1 кГц откалиброван
   по PIT, линии IOAPIC замаскированы → `__init_array` → `neko_kernel_init()` (регистрация `[Irq]`) → `sti` →
   `neko_kernel_main(&info)`.
3. Сгенерированный `neko_kernel_main` вызывает C#-метод с `[KernelEntry]`.

### Прерывания

| Векторы | Что |
|---|---|
| 0x00–0x1F | исключения CPU → `crash::cpu_exception` (экран смерти) |
| 0x20 | LAPIC-таймер 1 кГц → `time::uptime_ms` |
| 0x30–0x3F | ISA IRQ 0–15 через IOAPIC (с учётом interrupt source overrides) → обработчики `[Irq(n)]` |
| 0xFF | spurious |

`isr.S` (сгенерирован) кладёт номер вектора и код ошибки, сохраняет регистры в формате `crash::CpuState`,
`neko_isr_dispatch` отправляет исключения на экран смерти, остальное — в `irq_dispatch` (EOI для LAPIC).

### Потоки и планировщик

`core/sched.cpp` + `core/switch.S`. Поток — дескриптор в куче и стек 32 КиБ над guard-страницей (`vmm::create_stack`).
`neko_switch_context` кладёт на стек callee-saved регистры, RFLAGS и `fxsave` (576 байт) и загружает другой стек;
новый поток получает такой же кадр вручную и «возвращается» в `neko_thread_trampoline`. Таймер 1 кГц вызывает
`sched::tick()` после EOI: будит спящих, уменьшает квант (10 мс); в конце каждого IRQ `preempt_if_needed()` переключает
поток прямо из обработчика прерывания — кадр прерывания остаётся на стеке потока и `iretq` выполнится, когда до него
снова дойдёт очередь. Приоритеты High/Normal/Low — три FIFO; idle-поток (`sti; hlt`) работает, только когда они пусты.

Синхронизация (`core/sync.cpp`): `SpinLock` (atomic xchg + отключение прерываний, рекурсивный на одном CPU — куча
вызывает VMM, который снова выделяет память), `Mutex` (владелец + очередь ожидания; перед блокировкой проходит
цепочку «владелец → mutex, который он ждёт → …», и если она возвращается к текущему потоку — DEADLOCK), `Semaphore`
(signal из обработчиков прерываний). Под SpinLock работают куча и `term::write*`.

FPU/SSE: `arch/x86_64/entry.S` включает SSE (CR0/CR4) до первой C++-инструкции; `isr.S` делает `fxsave`/`fxrstor`
вокруг каждого обработчика, `switch.S` — вокруг каждого переключения, поэтому ядро собирается с SSE2 (без AVX).

### SMP

`arch/x86_64/smp.cpp`. Каждый CPU имеет запись `smp::Cpu` (GS base → `this_cpu()` за одну инструкцию): текущий
поток, idle-поток, квант, флаг перепланирования. AP запускаются запросом Limine MP: `neko_ap_entry` (entry.S) включает
SSE, `neko_ap_main` загружает наши таблицы страниц (EFER.NXE/PAT/WP — MSR на каждом CPU), свою GDT/TSS с IST-стеками,
общую IDT, GS base, LAPIC-таймер с калибровкой BSP, переходит на стек с guard-страницей и становится idle-потоком.

Планировщик один на всех: глобальные очереди под `g_lock`, который держится *через* переключение контекста — его
отпускает уже следующий поток (`after_switch`), поэтому поток не может начать выполняться на другом CPU, пока его
регистры не сохранены. Mutex/Semaphore блокируют поток через `sched::block(reason, &guard)`: внутренний замок примитива
отпускается только после захвата `g_lock`, так что пробуждение не теряется. IPI: 0xF0 — «есть работа» простаивающему
CPU, 0xF1 — TLB shootdown после `unmap/protect`, NMI — остановка остальных CPU, когда один рисует экран смерти.
Время (uptime) считает только BSP; спящих будит тоже он.

### Консоль

`core/console.cpp`: сетка ячеек (кодпоинт + цвета), перерисовываются только изменившиеся ячейки. Шрифт PSF1/PSF2
вшит через `.incbin` (`runtime/assets/fonts`, Terminus 8×16, OFL), таблица Unicode → глифы. Вход — байты UTF-8 и
ANSI-последовательности (`ESC[…m`, `ESC[2J`, `ESC[H`, `ESC[K`), поэтому один и тот же поток идёт и на экран, и в serial
(`neko::term`).

### Экран смерти

`core/crash.cpp`: STOP-код (векторы CPU 0x00–0x1F, программные 0xE0–0xE4), тип исключения (аппаратные — в терминах
.NET), сообщение, место в C#, стек вызовов по цепочке `rbp` (ядро собрано с `-fno-omit-frame-pointer
-fno-optimize-sibling-calls`), регистры, состояние системы; затем опрос клавиатуры (R — перезагрузка) при выключенных
прерываниях. Символы: ядро линкуется дважды — `scripts/gen-symbols.py` берёт из первого ELF функции (`llvm-nm`) и
таблицу строк DWARF (`llvm-dwarfdump`), пишет их в секцию `.neko_symbols`, которая стоит после `.bss`, поэтому адреса кода
во втором проходе не меняются (это проверяется `--verify`).

### Память

```
виртуальное адресное пространство (свои таблицы, vmm.cpp)
 0xffff800000000000  HHDM: вся RAM из карты памяти, 2 МиБ страницы, NX; framebuffer — write-combining (PAT 4)
 0xffffc00000000000  куча ядра: растёт по 1 МиБ+ (vmm::grow_heap → heap::add_region)
 0xffffd00000000000  свободно для VirtualMemory.Map
 0xffffe00000000000  стеки ядра: [guard 4 КиБ, не отображена][стек 64 КиБ] …
 0xffffffff80000000  образ ядра: .text RX, .rodata R, .data/.bss RW+NX, .neko_symbols R
```

- **Загрузка памяти**: `kmain` (на стеке Limine) — карта памяти → buddy-аллокатор → свои таблицы страниц
  (EFER.NXE, PAT, CR0.WP, `mov cr3`) → куча 4 МиБ → новый стек с guard-страницей → `kmain_main`.
  Таблицы Limine после этого не используются; bootloader-reclaimable память пока не освобождается (там ответы Limine).
- **Buddy** (`pmm.cpp`): каждая usable-область — зона; байт метаданных на кадр (`0x80 | order` у головы свободного
  блока) в начале области; двусвязные списки свободных блоков по порядкам 0…10 хранятся в самих блоках. Блоки выровнены
  по размеру в физических адресах; при освобождении склеиваются с «близнецом» (`pfn ^ 2^order`). Двойное освобождение
  → `HEAP_CORRUPTION`.
- **Куча** (`heap.cpp`): двусвязный список блоков в порядке адресов; заголовок 32 байта (`magic`, `size`, `prev`, `next`);
  first-fit; разбиение, если остаток ≥ 48 байт; слияние с соседями при освобождении и при `add_region`;
  `realloc` растёт на месте за счёт свободного соседа. Если места нет — `Grower` (VMM) отображает новые страницы сразу
  за концом кучи, и они сливаются со свободным хвостом. Неверный указатель или повторное освобождение → экран смерти.
  Без блокировок (одно ядро, без вытеснения) — фаза 4.
- **Переполнение стека**: запись в guard-страницу → #PF, который процессор не может положить на тот же стек → #DF на
  IST-стеке → экран смерти распознаёт адрес guard-страницы и пишет `StackOverflowException`.

### Пользовательский режим и процессы

`core/process.cpp`, `arch/x86_64/usermode.cpp`, `arch/x86_64/syscall.S`, ABI — `include/neko/process.hpp`.

```
адресное пространство процесса (нижняя половина; верхняя — общая с ядром)
 0x0000000000400000  образ программы: PT_LOAD-сегменты, R / RX / RW (+NX, где нет X)
 0x0000100000000000  память от системного вызова alloc (куча программы), растёт вверх, до 256 МиБ
 0x00007fffffff0000  вершина стека 256 КиБ; argv-строки и массив argv — на самом верху
```

- **Общая верхняя половина**: `vmm::init` заранее создаёт все 256 записей PML4[256…511], поэтому новое пространство
  копирует их один раз, а любые последующие отображения ядра (куча, стеки, MMIO) сразу видны во всех процессах.
- **Процесс = адресное пространство + потоки (до 64) + 32 файловых дескриптора + рабочий каталог.** `proc::spawn` читает
  программу из VFS (`/bin/NAME` или путь со `/`) во временный буфер, проверяет ELF (статический ET_EXEC x86_64, сегменты в
  пользовательской зоне, точка входа в исполняемом сегменте), отображает сегменты и стек через HHDM (пространство при
  этом не активно), кладёт argc/argv и запускает поток ядра `sched::spawn_for(process, …)`. Его первая функция загружает
  чистое состояние FPU и делает `iretq` в ring 3 (`neko_enter_user`, CS 0x23 / SS 0x1B, `swapgs`). Дескрипторы 0–2 и
  рабочий каталог наследуются от родителя (так `sh` делает перенаправления: `dup` → `dup2` → `spawn` → `dup2` обратно);
  детям ядра достаются три ссылки на `/dev/console`. Файлы закрываются, когда снят с CPU последний поток.
- **Переключение**: перед каждым `neko_switch_context` хук `neko_sched_switch_to` ставит `TSS.rsp0` и `gs:8` на вершину
  стека ядра входящего потока и загружает его CR3 (у потоков ядра — таблицы ядра).
- **`syscall`**: STAR = 0x08/0x10 (sysret → 0x23/0x1B), SFMASK гасит IF/DF/TF/AC. `neko_syscall_entry` делает `swapgs`,
  переходит на стек ядра потока, строит `SyscallFrame` (как кадр прерывания без вектора), `fxsave`, `sti` и вызывает
  `neko_syscall_dispatch`. Номер — `rax`, аргументы — `rdi rsi rdx r10 r8 r9`, результат — `rax` (отрицательный = ошибка).
  Встроенные вызовы 0–31 (exit, read, write, getpid, yield, sleep, uptime, spawn, wait, alloc, process_info, kill,
  thread_create, thread_exit, thread_id и файловые 16–29: open, close, seek, stat, fstat, readdir, mkdir, remove,
  dup, dup2, chdir, getcwd, rename, truncate) — в C++; номера от 32 регистрирует C#-код ядра атрибутом `[Syscall(n)]`.
  `read`/`write` идут через таблицу дескрипторов процесса в VFS (через промежуточный буфер ядра по 16 КиБ);
  чтение `/dev/console` — построчный ввод с клавиатуры на C# (`kernel/Syscalls.neko`, `Vfs.SetConsoleReader`).
  Ядро читает и пишет память программы только через `proc::copy_from_user/copy_to_user` (`neko_user_copy` в
  `syscall.S`): проверка диапазона, `stac`/`clac` вокруг `rep movsb`, а #PF внутри копирования `idt.cpp` переводит на
  метку-исправление — вызов возвращает `ErrBadAddress`, ядро не падает. Где CPU умеет, включены SMEP (ring 0 не исполняет
  страницы программ) и SMAP (любой другой доступ к ним — #PF). `check_read/check_write` (`UserMemory.CanRead`) —
  предварительная проверка по таблицам страниц, например чтобы `read` отказал до ожидания ввода.
- **Прерывания из ring 3**: `isr.S` смотрит на CS в кадре и делает `swapgs` на входе и выходе. Исключение CPU в ring 3
  не вызывает экран смерти: `proc::user_exception` печатает .NET-имя исключения, адрес и `rip` и завершает процесс с
  кодом 128 + вектор (`#PF` → 142, `#GP` → 141, `#UD` → 134).
- **Завершение**: `exit`, `kill`, Ctrl+C или падение фиксируют код выхода (первый побеждает) и ставят `kill_pending` всем
  потокам процесса; `sched::interrupt` обрывает `sleep` и прерываемые ожидания (`Semaphore::wait_interruptible`:
  флаг и `waiting_sem` публикуются в порядке, при котором пробуждение не теряется). Поток завершается на пути обратно в
  ring 3: в конце `neko_syscall_dispatch` и после прерывания из ring 3 (поток на другом CPU будится IPI). Когда снят с
  CPU последний поток, `proc::thread_freed` освобождает нижнюю половину, отдаёт сирот ядру (они освобождаются сами) и
  будит родителя в `wait`. Фоновые (`detached`) процессы освобождаются сразу.
- **Передний план**: `g_foreground` — pid владельца консоли. `wait` передаёт консоль ребёнку на время ожидания
  (shell ядра → `sh` → программа), Ctrl+C в драйвере клавиатуры (`Process.InterruptForeground`) завершает его с кодом 130.
- **Потоки программы**: `thread_create(rip, stack, arg)` — ещё один поток ядра того же процесса; рантайм выделяет стек
  64 КиБ из кучи, `neko_user_thread_entry` (crt0.S) после возврата функции ставит `done` и вызывает `thread_exit`, уже не
  касаясь стека, поэтому `Thread.Join` может сразу его освободить. Куча и буфер вывода защищены `Lock` (спин + `yield`).

Рантайм программ (`runtime/user/`): `crt0.S` (`_start` → `neko_user_start`: `__init_array`, `Main`, `exit`), обёртки
системных вызовов, буферизованный вывод (сброс на `\n`, перед `read` и при выходе), first-fit куча поверх `alloc`,
`str::*`, потоки и `Lock`, а `throw`/`Debug.Assert` печатают сообщение и завершают программу с кодом 134. C#-API —
`sdk/Nekotia.User` (`Console`, `Process`, `File`, `Path`, `Thread`, `SpinLock`, `Atomic`, `Memory`, `Time`); `Attributes.cs`, `Intrinsics.cs`, `Debug.cs`, `Maths.cs` общие с ядром.

### Файловая система

`core/vfs.cpp`, API — `include/neko/vfs.hpp`, C# — `sdk/Nekotia.Sdk/IO/Vfs.cs` (ядро) и `sdk/Nekotia.User/File.cs` (программы).

```
/            ramfs: узлы и содержимое файлов в куче ядра
/bin /etc …  из initrd (build/initrd.tar → модуль Limine): файлы указывают прямо в модуль до первой записи
/dev         console (клавиатура + экран), null, zero
/tmp         пустой каталог
```

- **Одно дерево узлов** (`Node`: имя, тип, родитель, дети, данные или `DeviceOps`). Пути — абсолютные или от рабочего
  каталога (у процесса свой, у потоков ядра — общий); `.` и `..` разбираются при обходе.
- **Подсчёт ссылок**: узел держит ссылку, пока он в дереве, плюс по одной на открытый файл и рабочий каталог. `remove`
  только отцепляет узел — открытый файл продолжает читаться, память уходит с последней ссылкой. Открытый файл (`File`:
  узел, смещение, флаги) тоже со счётчиком: `dup` и наследование делят смещение.
- **Блокировка**: один spin lock на дерево и смещения. Вызовы устройств идут без него (консоль ждёт строку), копирования
  под ним ограничены 16 КиБ (размер промежуточного буфера системных вызовов).
- **initrd**: ustar (`name` + `prefix`, проверка контрольной суммы), каталоги создаются по пути, ссылки пропускаются.
  Запись в файл из initrd сначала копирует его в кучу (copy-on-write); `df` показывает, сколько ещё читается из модуля.
  Модуль, который не tar, становится `/bin/ИМЯ` — так можно подложить программу строкой `module_path`.

### Каналы

`vfs::pipe` создаёт безымянный узел-устройство (не в дереве) и два открытых файла на нём: только для чтения и только для
записи. Буфер — кольцо 64 КиБ под своим spin lock; ждущие читатели и писатели спят на двух семафорах
(`wait_interruptible`, так что `kill` и Ctrl+C их будят), а каждое изменение будит всех ждущих той стороны — они
перепроверяют условие. У устройств VFS для этого есть `close(flags)` (последнее закрытие конца уменьшает число
читателей/писателей) и `release`. Пустой канал без писателей — конец ввода (0), запись без читателей — `kErrBrokenPipe`,
и системный вызов `write` тогда завершает программу с кодом 141, как SIGPIPE. `sh` строит конвейер так: для каждого
звена переключает свои 0/1 на нужные концы (`dup2`), запускает программу, возвращает 0/1 и закрывает свои копии
концов — иначе читатель никогда не увидел бы конец ввода.

### Сеть

Драйвер — `drivers/virtio_net.cpp` (C++, общий с диском транспорт `drivers/virtio.cpp`): очередь приёма с 64
постоянно выставленными буферами по 2 КиБ, очередь отправки со слотами, одно MSI-X-прерывание на обе. Принятые
кадры прерывание копирует в кольцо интерфейса (`core/netif.cpp`), откуда их забирает стек.

Стек — **C#**, `kernel/Net/`: поток `net-rx` ждёт кадры (`NetDevice.Receive`) и разбирает их под мьютексом стека
(`Stack.Lock`), поток `net-timer` раз в 100 мс ведёт таймеры TCP и закрывает сокеты, освобождённые процессами.
Отправители собирают пакет в общем буфере под тем же мьютексом; MAC следующего узла они узнают *до* этого
(`Arp.Resolve` спит), поэтому поток приёма никогда не ждёт их.

| Файл | Что делает |
|---|---|
| `Net.neko` | интерфейс, порядок байт, контрольные суммы, Ethernet, маршрут (подсеть или шлюз), разбор адресов |
| `Arp.neko` | кэш на 32 записи (из ответов, запросов к нам и любого входящего IPv4), ответы на запросы |
| `Ip.neko` | заголовок и проверка, loopback (кадр снова попадает в кольцо приёма), без фрагментации |
| `Icmp.neko` | эхо-ответы и ping |
| `Udp.neko` | сокеты: порт и очередь из 8 датаграмм с отправителем |
| `Dhcp.neko` | DISCOVER → OFFER → REQUEST → ACK: адрес, маска, шлюз, DNS |
| `Dns.neko` | запрос A-записи к DNS из DHCP, сжатые имена, кэш на минуту |
| `Tcp.neko` | соединения (32): машина состояний RFC 9293, буферы по 16 КиБ, окно и пробы нулевого окна, обновления окна, MSS, повторная передача с удвоением RTO (8 попыток), FIN в обе стороны, RST, TIME_WAIT 2 с |
| `Sockets.neko` | сокеты как файлы (`vfs::open_socket`) и системные вызовы 40–48 на C# (`@syscall`) |

Сокет — обычный файловый дескриптор: `read`/`write` идут через VFS в `Tcp.Receive`/`Tcp.Send`, `dup2` и
перенаправления работают, `write` в разорванное соединение завершает программу с кодом 141. Последний `close` может
случиться при разрушении процесса, где спать нельзя, поэтому он лишь помечает сокет под spin lock, а закрывает
его `net-timer`. Нет: контроля перегрузки, SACK, масштабирования окна, IPv6, приёма сегментов не по порядку (их
отбрасывают и повторяют ACK — отправитель перешлёт).

### Диски

`core/block.cpp` (API — `include/neko/block.hpp`, C# — `sdk/Nekotia.Sdk/IO/Block.cs`) — реестр блочных устройств:
драйвер даёт `read/write/flush` секторами, слой добавляет проверку границ, статистику, узел `/dev/ИМЯ` (устройство VFS с
размером: `seek`, побайтовые чтение и запись, неполные секторы — через чтение-изменение-запись) и RAM-диски (в host-режиме
самотест работает на `ram0`).

`drivers/virtio_blk.cpp` — virtio 1.x («modern» PCI): окна common/notify/device из vendor-capabilities в BAR,
сброс → ACKNOWLEDGE → DRIVER → признаки (VERSION_1, RO, FLUSH) → FEATURES_OK → очередь 0 → DRIVER_OK. Одна split-очередь
до 64 дескрипторов в одной странице; запрос — постоянная цепочка из трёх дескрипторов (заголовок, данные, статус) на
слот, у каждого из 8 слотов свой DMA-буфер 64 КиБ (буферы вызывающих не обязаны быть физически непрерывными).
Завершение — MSI-X: `irq::allocate_msi` выдаёт вектор 0x40…0xEF, `pci::msix_route` пишет адрес LAPIC и вектор в таблицу,
обработчик разбирает used-кольцо и будит ждущий поток (семафор слота); без MSI-X поток опрашивает кольцо с `yield`.
`drivers/ahci.cpp` — SATA: контроллер AHCI (на q35 он встроен, к нему же подключён загрузочный CD). Для каждого
активного порта — список команд, область принятых FIS и по таблице команд на слот (FIS + одна запись PRDT на
64-КиБ DMA-буфер слота). ATA-диски (`sda…`): IDENTIFY, READ/WRITE DMA EXT с 48-битным LBA, FLUSH CACHE EXT.
ATAPI (`cd0…`): PACKET с SCSI READ(10) и READ CAPACITY, секторы по 2048 байт, только чтение. Завершение — MSI:
обработчик сравнивает биты PxCI с выданными слотами; ошибка (TFES) завершает выданные слоты с `kErrIo` и
перезапускает порт. Без 64-битного DMA контроллер пропускается (буферы могут лежать выше 4 ГиБ).

`make run` подключает `build/disk.img`, `make test` — свежий 8-МиБ диск, на который пишет самотест (обычная загрузка
на диск не пишет), а также SATA-диск `sda` с тем же самотестом и чтение `cd0`.

### FAT32

`fs/fat.cpp` (API — `include/neko/fat.hpp`, C# — `Nekotia.IO.Fat`). Драйвер файловой системы подключается к VFS
через `FsOps` (`vfs::mount`): при монтировании всё дерево каталогов читается в узлы VFS (у каждого — `Entry`: первый
кластер и где лежит его 32-байтная запись), поэтому обход путей идёт без диска под spin lock VFS, а чтение, запись,
создание, удаление и переименование VFS вызывает уже без замка — том сериализует их своим `Mutex`.

- **Запись сразу**: данные, обе копии FAT (через кэш из 16 секторов), записи каталогов и размеры пишутся в момент
  изменения, поэтому `close` не делает ввода-вывода (его можно звать откуда угодно, даже из `thread_freed`), а
  выключение без `umount` теряет только подсказку FSInfo (её пишут `sync`, `umount`, `reboot`, `shutdown`).
- **Имена**: длинные имена VFAT читаются и пишутся (UTF-16, проверка контрольной суммы); имя 8.3 в одном регистре
  хранится без них (с флагами нижнего регистра NT, как это делают Windows и Linux), иначе создаётся псевдоним `NAME~N.EXT`.
- **Ограничения**: удалить открытый файл нельзя (`ErrBusy` — кластеры освобождаются сразу), переименование только
  внутри тома (`mv` между томами копирует), файлы до 4 ГиБ, дат нет (нет RTC — пишется 2026-01-01).
- **`mkfs`**: 32 зарезервированных сектора, 2 FAT, кластеры по таблице Microsoft, ≥ 65525 кластеров (иначе другие
  системы сочтут том FAT16), FSInfo и резервная копия загрузочного сектора, метка тома.
- **Проверка**: самотест форматирует второй диск `make test`, пишет, перемонтирует и сверяет, а затем
  `scripts/fatcheck.py` — независимый проверяльщик по спецификации — проверяет образ: копии FAT, цепочки,
  пересечения и потерянные кластеры, LFN, `.`/`..`, FSInfo — и читает оставленный файл с кириллическим именем.

### PCI

`arch/x86_64/pci.cpp`, API — `include/neko/pci.hpp`, C# — `sdk/Nekotia.Sdk/Hal/Pci.cs`. Конфигурационное пространство —
ECAM из таблицы ACPI MCFG (каждая функция — своя 4-КиБ MMIO-страница, отображается по требованию) или, без MCFG, порты
`0xCF8/0xCFC`. Обход шины 0 (и корневых шин мульти-функционального host bridge) идёт рекурсивно через PCI-to-PCI мосты;
для каждой функции запоминаются id, класс, IRQ и BAR с размерами (запись `0xFFFFFFFF` при выключенном декодировании).
Драйверы ищут устройства через `Pci.Find`/`FindClass`, включают `Enable(memory, io, busMaster)` и отображают `MapBar`.

### Исключения

`isr.S` выравнивает кадр стека (код ошибки 0 для исключений без него), сохраняет все GPR и вызывает
`neko_isr_dispatch(InterruptFrame*)`, который печатает вектор, имя, `rip`, `rflags`, регистры, для `#PF` — `cr2` и причину,
затем `panic`. `addr2line -e build/nekotia.elf <rip>` даёт C#-строку.

## Host-режим

Тот же рантайм (`src/core`) + `src/host/host_main.cpp` вместо `arch/` и `freestanding/`, сборка обычным clang++ с
ASan/UBSan. Куча и фреймы — из `aligned_alloc`, HHDM = 0, framebuffer 800×600 в RAM (сохраняется в
`build/host/framebuffer.ppm`), serial → stdout, `Cpu.Halt()` завершает процесс, `asm` вырезается.
Нужен для быстрых проверок транспилятора и алгоритмов; всё, что связано с железом, проверяется только в QEMU.
